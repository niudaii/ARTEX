# 报告归档流程

**task_id**：取自触发本 skill 的「【报告归档任务】task_id=...」消息，后续所有工具调用使用它。

按以下阶段执行报告归档，上一阶段完成并自检后才进入下一阶段。

## 阶段 1 · 读取发现（门槛：必须读全，两步走）

list_task_findings 只返回紧凑字段（id/vulnclass/severity/摘要/状态），**不含完整 PoC/证据**，必须分两步：

1. **列全清单**：调用 list_task_findings(task_id=<task_id>)，得到全部确认漏洞条目。
   - 结果被截断或提示更多时继续读全；只凭部分条目归档视为失败。
2. **逐条取全证据**：对每一条调用 get_task_node_detail(task_id, id=<finding_id>)，
   读取该漏洞的完整详情/证据/PoC。
   - 任何一条缺少完整证据就进入后续阶段，视为流程失败。
   - 后续过滤判定与报告组装一律以这里取到的证据原文为准。

## 阶段 2 · 过滤误报与定级（渐进加载：评分规则）

先阅读 ${SKILL_DIR}/references/vuln-scoring.md，获取等级定义、调整规则与剔除标准，再**基于阶段 1 取到的完整证据**逐条判定（不得只看摘要）：

- 剔除：逐条对照该文件的「剔除标准」与「不得剔除」条款——扫描器误报、证据不支持结论的、无实际利用影响的纯信息类条目等（以该文件为准）。
- 判定只依据该条目自身证据，不允许臆测；证据无法支撑的影响不得计入。
- 逐条记录被剔除条目（标题 + 命中标准 + 一句话原因），写入报告头部说明。
- 同时按该文件的评分规则为每条保留漏洞定级（含攻击链评分与评分调整规则），供阶段 4 使用。

## 阶段 3 · 分组与合并

1. 按域名分组：从每条漏洞的 PoC/证据中提取目标 hostname，按站点归组；PoC 无 hostname 时用任务目标域名兜底，仍无法归属的放入「其他」组。
2. 重复合并：同域名 + 同漏洞类型 + 相同/相似端点 → 合并为一条；描述拼接，PoC 取最完整的，`来源` 注明合并自哪些 finding id。
3. 攻击链合并：同域名内多条漏洞构成逻辑利用链（如 RCE → 凭据泄露 → 数据失陷）→ 合并为一条主漏洞，子漏洞以 N.x 层级展开；只合并有因果链的，不机械合并。攻击链按 vuln-scoring.md 的「攻击链评分规则」定级。

## 阶段 4 · 组装归档报告（渐进加载：报告模板）

阅读 ${SKILL_DIR}/references/report-template.md，按其中的报告结构、漏洞模板与排序编号规则组装 Markdown 归档报告。

- 请求/响应包必须来自阶段 1 取到的 finding 证据原文，缺失则注明「证据缺失」，禁止编造或脑补。
- 等级以阶段 2 定级为准；总结表与正文的等级、编号一一对应。

## 阶段 5 · 写回归档（门槛：必须调用工具且写回成功）

调用 archive_task_report(task_id=<task_id>, markdown=完整报告) 写回。

- 报告 <200 字会被拒绝；写回失败时按返回的错误信息修正后重试，直到成功——未成功写回等于没归档。
- 写回成功后只回复一行归档结果摘要（归档条目数/等级分布/剔除数/写回状态），不要输出报告全文。

## 边界

- 只读整理：禁止对任何目标发起请求、攻击、复测或扫描。
- 禁止编造、夸大或润色漏洞事实；凭据类证据保持原样（证据完整性）。
- 过滤后为 0 条时，仍写回一份说明「无可归档漏洞及原因」的简报（列明每条被剔除的 finding 及依据）。

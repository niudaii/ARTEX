# 漏洞复测治理

## 原则

模型已具备丰富的漏洞验证知识。本 skill 不堆砌 payload，只提供
**复测决策矩阵**和**修复判定标准**——让模型系统化地重放原始 PoC、
对比响应差异、判定漏洞是否已修复，而非凭单次请求猜测结论。

复测的核心是**可复现性对比**：用与原始报告相同（或等价）的 PoC 重新触发，
对比原始漏洞特征是否消失。结论只有三种：✅ 已修复 / ❌ 未修复 / ⚠️ 无法确定。

---

## PoC 边界

| 禁止 | 允许 |
|------|------|
| 复测时执行破坏性操作（删除/修改数据） | 只读验证，证明漏洞存在或消失 |
| 对非原始报告中的目标执行测试 | 仅重放原始 PoC 中的目标资产 |
| 越权读取他人数据验证越权漏洞 | 用自己的账号验证越权逻辑是否仍存在 |
| 大规模遍历验证 IDOR | 读取 1 条记录证明可/不可访问 |
| 持久化 webshell 或后门 | 执行 `id`/`whoami`/`sleep 1` 证明 RCE 仍存在 |

---

## 复测流程

### Step 1：确定漏洞来源并获取漏洞详情

支持两种漏洞来源，根据任务输入自动选择：

#### 来源 A：ARTEX finding 系统

当任务输入为 ARTEX finding ID、任务上下文中的漏洞、或要求复测本平台已报漏洞时：

```
list_findings  → 获取所有确认漏洞（id + vulnclass + severity + summary + state）
node_detail(id) → 获取单条漏洞完整详情（PoC / 证据 / 资产关联）
```

- 任务指定复测特定漏洞 → 用 `node_detail(id)` 逐条读取详情。
- 任务要求全量复测 → 逐条 `node_detail` 读取所有 finding。
- finding 列表为空 → 报告「无已报漏洞可复测」，结束。

#### 来源 B：SOC 漏洞平台（socctl）

当任务输入为 SOC 漏洞链接（`https://soc.netease.com/#/vulnerability/detail/<数字>`）
或纯漏洞 ID（纯数字），且要求复测 SOC 漏洞时：

```bash
socctl detail <漏洞链接或纯数字 ID>
```

从输出中提取关键字段：

| 字段 | 输出标记 | 必填 |
|------|---------|------|
| 漏洞 ID | `漏洞 ID:` | 是 |
| 标题 | `标题:` | 是 |
| 状态 | `状态:` (FIXED/OPEN等) | 是 |
| 等级 | `等级:` (HIGH/MODERATE/LOW) | 是 |
| 类型 | `类型:` | 是 |
| 目标资产 | `目标资产:` | 是 |
| 描述/PoC | `描述:` 后的文本（含 HTTP 请求 / URL / 复现步骤） | 是 |
| 链接 | `链接:` | 否 |

- `socctl detail` 调用失败 → 提示接口异常，**终止**。
- 描述中无 PoC / HTTP 请求 / 复现步骤 → 判 `⚠️ 无法确定`，原因「报告缺少 PoC」，跳到 Step 4。
- SOC 漏洞状态已为 `FIXED` → 仍执行复测验证（状态可能未更新），以实际复测结果为准。

#### 来源判断规则

| 输入特征 | 来源 |
|---------|------|
| 任务上下文中有 ARTEX finding / 要求复测平台漏洞 | A：ARTEX finding |
| `soc.netease.com` 链接 / 纯数字 ID / 明确要求复测 SOC 漏洞 | B：SOC 漏洞 |
| 混合输入（既有 ARTEX finding 又有 SOC 链接） | 两种来源分别处理 |

### Step 2：提取原始 PoC 与漏洞特征

**来源 A（ARTEX finding）**，从 `node_detail` 返回的详情中提取：

| 字段 | 提取规则 | 必填 |
|------|---------|------|
| 漏洞类型 | `vulnclass` 字段 | 是 |
| 严重等级 | `severity` 字段 | 是 |
| PoC / 证据 | `evidence.poc` 或 `evidence` 文本中的 HTTP 请求/命令/步骤 | 是 |
| 目标资产 | PoC 中的 URL / Host / IP | 是 |
| 原始漏洞特征 | PoC 触发时的响应特征（回显/错误/敏感数据/payload 执行） | 是 |
| 受影响资产 ID | `asset_ids`（用于关联） | 否 |
| 发现过程 | `detail` / `evidence` 文本中漏洞的发现路径简述（哪个 work/意图发现了它、怎么发现的） | 否 |

**来源 B（SOC 漏洞）**，从 `socctl detail` 输出的描述文本中提取：

| 字段 | 提取规则 | 必填 |
|------|---------|------|
| 漏洞类型 | 根据描述内容推断（SQL注入/XSS/SSRF/越权等） | 是 |
| 严重等级 | `等级:` 字段映射：HIGH→high, MODERATE→medium, LOW→low | 是 |
| PoC / 证据 | `描述:` 后的 HTTP 请求 / URL / 复现步骤 | 是 |
| 目标 URL | 请求中的 Host + Path 或描述中的 URL | 是 |
| 原始漏洞表现 | 描述中漏洞触发的响应特征（回显/错误/敏感数据/payload 执行） | 是 |
| 认证信息 | PoC 中的 Cookie / Token / Session（可能已过期） | 否 |
| 发现过程 | `描述:` 文本中漏洞的发现路径简述（测试人员怎么发现的、什么场景下触发的） | 否 |

**通用处理**：
- 无 PoC / 证据不足 → 判 `⚠️ 无法确定`，原因「原始报告缺少可复现 PoC」。
- PoC 中的目标资产不在当前任务授权范围 → 判 `⚠️ 无法确定`，原因「目标不在授权范围」。

### Step 3：分类复测策略

根据 `vulnclass` 选择复测方式：

| 漏洞类型 | 复测方式 | 证据要求 |
|---------|---------|---------|
| SQL 注入、命令注入、XXE、文件上传、信息泄露、URL 重定向 | HTTP 重放原始 PoC | 请求 + 响应对比 |
| 反射型 XSS | HTTP 重放 + 浏览器 DOM 验证 | 请求 + 响应 + DOM 截图 |
| 存储型 XSS / DOM 型 XSS | 浏览器访问目标页面验证 | DOM 截图 |
| SSRF（有回显） | HTTP 重放 | 请求 + 响应 |
| SSRF（无回显 / OOB） | HTTP 重放 + Collaborator/DNSLog 检测 | 请求 + OOB 交互记录 |
| 越权 / IDOR | HTTP 重放（用非授权账号凭据） | 请求 + 响应 |
| 认证绕过 / 弱口令 | HTTP 重放验证认证逻辑 | 请求 + 响应 |
| 逻辑漏洞 / CSRF | 浏览器操作验证 | 操作截图 |
| RCE / 命令注入 | HTTP 重放原始 payload | 请求 + 响应（命令输出） |
| 反序列化 | HTTP 重放原始 payload | 请求 + 响应 |
| 已知 CVE | 按 CVE 原始 PoC 重放 | 请求 + 响应 |
| 无法自动复测（物理安全、社工、需特定环境） | ⚠️ 无法确定 | — |

**认证信息处理**：
- 原始 PoC 中的 Cookie/Token 可能已过期。
- 需要认证且原始凭据已失效 → 请用户提供有效会话凭据后继续。
- 越权类漏洞：需使用**非授权账号**的凭据重放。

### Step 4：执行复测

#### 4a：HTTP 重放

用 `curl` 或 Python `requests` 重放原始 PoC 请求。

- 保持原始 PoC 的 Method / Path / Headers / Body **完整不变**。
- 用户提供了新凭据时替换原始凭据字段。
- 不修改与漏洞无关的参数。
- HTTPS 目标始终忽略证书验证（`-k` / `verify=False`）。
- 必须设置超时：curl `--max-time 10 --connect-timeout 5`；Python `timeout=(5, 10)`。

**OOB 检测**（盲 SSRF / 无回显注入）：
- 使用 Burp Collaborator 或 DNSLog 生成监听地址。
- 替换 PoC 中的目标地址为监听地址 → 重放 → 等待 3-5 秒 → 检查交互记录。
- 有交互 → 漏洞仍存在；无交互 → 结合响应内容综合判断。

#### 4b：浏览器验证

对于需要浏览器验证的漏洞（XSS / DOM 型 / 逻辑漏洞 / CSRF）：

1. 用浏览器打开目标 URL（原始 PoC 中的完整 URL）。
2. 触发漏洞条件（注入 payload / 执行操作 / 访问存储型 XSS 页面）。
3. 检查 DOM 中是否出现 payload 执行证据。
4. 截图保存证据。

**XSS 验证标准**（严格执行）：
- 仅 HTTP 响应中含 payload **不等于**漏洞存在——必须浏览器 DOM 中 payload **实际执行**。
- 响应中 payload 被 React/Vue/框架转义 → DOM 未执行 → **不算漏洞存在**。
- 反射型 XSS：重放响应中 payload 未转义 → 浏览器访问确认 DOM 中 payload 实际执行。
- 存储型 XSS：浏览器访问目标页面 → 检查 DOM 中是否还有存储的 payload 且实际执行。

#### 4c：对比分析

将复测响应与原始漏洞报告中的预期表现对比：

| 对比结果 | 判定 |
|---------|------|
| 响应中不再包含漏洞特征（注入回显消失/错误消失/敏感数据不可见/payload 未执行） | ✅ 已修复 |
| 响应仍包含漏洞特征（与原始报告一致或等价） | ❌ 未修复 |
| 请求被拦截（403/WAF/参数过滤/输入编码） | ✅ 已修复（注明修复方式：WAF/参数过滤/输入编码） |
| 请求被拦截但 WAF 规则可绕过 | ❌ 未修复（注明 WAF 绕过路径） |
| 目标不可达 / 连接超时 | ⚠️ 无法确定（原因「目标不可达」） |
| 认证失败（401/403 但非修复） | ⚠️ 无法确定（原因「认证失效，需有效凭据」） |
| 原始 PoC 不完整无法重放 | ⚠️ 无法确定（原因「PoC 不完整」） |

### Step 5：记录复测结果

**来源 A（ARTEX finding）**：用 `record_fact` 记录复测结论：

```
record_fact(
  summary: "复测: {漏洞标题} → {✅已修复/❌未修复/⚠️无法确定}",
  detail: "原始漏洞: {vulnclass} {severity}\n复测方式: {HTTP重放/浏览器验证/OOB}\n复测证据: {响应摘要/截图路径/OOB记录}\n结论: {判定理由}"
)
```

若复测确认漏洞**仍存在**且原始 finding 状态已变，可用 `report_finding` 更新或追加复测记录。

**来源 B（SOC 漏洞）**：将复测结论写入任务输出，供人工在 SOC 平台更新漏洞状态。
不自动调用 `socctl` 的写命令（mark-duplicate / mark-ignore）——这些是 side-effect 操作，
需人工确认。

#### 通知主人（复测未通过时）

当复测结果为 **❌ 未修复** 时，**必须**调用 `send_me` 工具给主人发一条 POPO 通知消息，
格式如下：

```
send_me({
  "message": "漏洞复测未通过 — 漏洞标题：{漏洞标题}，漏洞链接：{漏洞链接/SOC链接/ARTEX finding URL}，ARTEX 任务链接：{当前任务链接}"
})
```

- 仅在结果为 ❌ 未修复时发送（✅ 已修复 / ⚠️ 无法确定 不发）。
- 多条漏洞未修复时，合并为一条消息逐条列出，或逐条发送。
- ARTEX 任务链接可从当前任务上下文获取；SOC 漏洞链接即原始输入的 SOC 漏洞 URL。

#### 关联漏洞与攻击链

复测完所有漏洞后，在输出报告前，检查漏洞之间的关联关系：

1. **关联漏洞**：用 `list_findings` 获取全部已确认漏洞，识别与本批复测漏洞相关的：
   - 同一目标资产/端点的漏洞（同 host、同接口）
   - 同一攻击面的漏洞（同参数、同功能模块）
   - 同一漏洞类型的漏洞（多个 SQL 注入、多个 XSS）
   记录关联漏洞的 ID 和关系。

2. **攻击链路**：若多个漏洞可串成完整利用链（如：信息泄露 → SSRF → RCE），
   按链路顺序整理，标注每环的漏洞 ID 和串联逻辑。
   - 仅当漏洞间确实存在利用依赖时才整理链路，不要牵强组合。
   - 单个独立漏洞无需链路，跳过此项。

### Step 6：输出复测报告

逐条输出复测结果，格式：

```
----------------------------------------------
 漏洞复测报告
----------------------------------------------
 漏洞 ID   : {finding_id}
 标题      : {漏洞标题}
 类型      : {vulnclass}
 等级      : {severity}
 复测结果  : {✅ 已修复 / ❌ 未修复 / ⚠️ 无法确定}
 复测方式  : {HTTP 重放 / 浏览器验证 / OOB 检测 / —}
 复测证据  : {响应关键摘要 / OOB 交互记录 / 截图路径 / 原因说明}
 发现过程  : {原始漏洞发现路径简述：谁在什么场景下怎么发现的}
 关联漏洞  : {相关漏洞 ID 及关系，无则填「无」}
 攻击链路  : {多漏洞链路简述，单漏洞则填「—」}
 复测时间  : {YYYY-MM-DD HH:MM}
----------------------------------------------
```

多个漏洞时逐条输出，最后追加汇总：

```
----------------------------------------------
 复测汇总：共 {N} 条
----------------------------------------------
 漏洞 ID | 标题           | 结果
---------|----------------|----------------
 101     | SQL注入-login   | ✅ 已修复
 102     | XSS-搜索反射    | ❌ 未修复
 103     | SSRF-回调接口   | ⚠️ 无法确定（目标不可达）
----------------------------------------------
```

## 修复判定标准

### ✅ 已修复的判定条件（任一满足）

| 修复方式 | 判定依据 |
|---------|---------|
| 代码修复 | 原始 PoC 重放后漏洞特征完全消失（无回显/无错误/无敏感数据/payload 未执行） |
| 输入验证 | 原始 payload 被过滤/编码/拒绝，且无法通过编码变换绕过 |
| 访问控制 | 原始攻击路径返回 403/401，且无法通过 bypass-403 技巧绕过 |
| WAF 拦截 | 原始 payload 被 WAF 拦截，且无法通过编码/分隔符/大小写绕过 |

### ❌ 未修复的判定条件

- 原始 PoC 重放后漏洞特征**仍然存在**（与原始报告一致或等价）。
- WAF 拦截但可通过编码变换/分隔符注入/大小写混淆绕过。
- 输入过滤但可通过双重编码/Unicode/替代字符绕过。
- 认证逻辑变更但可通过其他路径绕过。

### ⚠️ 无法确定的判定条件

- 原始报告缺少可复现 PoC。
- 目标不可达 / 连接超时（非修复导致）。
- 认证凭据已失效且无法获取新凭据。
- 漏洞类型无法自动复测（物理安全、社工等）。
- 环境依赖不满足（需特定中间件/配置/数据）。

## 错误处理

| 场景 | 处理方式 |
|------|---------|
| `list_findings` 返回空 | 报告「无已报漏洞可复测」，结束 |
| `node_detail` 无 PoC / 证据 | 判 ⚠️ 无法确定，原因「报告缺少 PoC」 |
| `socctl detail` 调用失败 | 提示 SOC 接口异常，终止该条复测 |
| SOC 漏洞描述无 PoC / HTTP 请求 | 判 ⚠️ 无法确定，原因「报告缺少 PoC」 |
| 目标不可达 / 连接超时 | 判 ⚠️ 无法确定，原因「目标不可达」 |
| 认证失败（401/403 但非修复） | 请用户提供有效凭据后重试 |
| 浏览器验证失败 | 尝试 HTTP 重放，均失败则判 ⚠️ 无法确定 |
| OOB 无交互 | 不单独判定，结合响应内容综合判断 |
| 多漏洞中某条失败 | 记录失败原因，继续下一条 |

## 超时铁律

| 约束 | 值 |
|------|-----|
| curl 超时 | `--max-time 10 --connect-timeout 5` |
| Python requests | `timeout=(5, 10)` |
| 单条漏洞复测上限 | 3 分钟 |
| OOB 等待时间 | 3-5 秒 |
| 全量复测上限 | 15 分钟 |
| HTTPS 证书 | 始终忽略（`-k` / `verify=False`） |

---

## 安全注意

- 复测请求仅发送到原始漏洞报告中标注的目标资产。
- 不对非授权目标执行任何测试。
- 截图中不含敏感凭据信息（Cookie/Token 打码处理）。
- WAF 拦截不等同于修复，需区分判断（检查是否可绕过）。
- 复测不产生新的破坏性副作用。

---

## 🚫 禁止操作

| # | 🚫 禁止行为 | 正确做法 |
|---|-----------|---------|
| 1 | 仅看 HTTP 响应中有 payload 就判定 XSS 仍存在 | 必须浏览器验证 DOM 中 payload 实际执行 |
| 2 | 对非原始报告中的目标执行测试 | 仅重放原始 PoC 中的目标资产 |
| 3 | 将 WAF 拦截直接判定为已修复 | 检查 WAF 规则是否可绕过，可绕过则判未修复 |
| 4 | 使用非枚举结论（如「部分修复」「待观察」） | 仅三种结论：✅ 已修复 / ❌ 未修复 / ⚠️ 无法确定 |
| 5 | 复测时执行破坏性操作 | 只读验证，证明漏洞存在或消失 |
| 6 | 截图中暴露 Cookie/Token 等敏感凭据 | 打码处理后保存 |
| 7 | 修改原始 PoC 的核心参数 | 保持 Method/Path/Headers/Body 完整，仅替换过期凭据 |

---

## 完成定义

**Positive exit**：
- 所有待复测漏洞均已执行复测并输出结论。
- 每条结论有可核验的证据（响应摘要/OOB 记录/截图路径）。
- 复测报告含逐条结果 + 汇总表。

**Negative exit**：
- 所有漏洞均判定为 ⚠️ 无法确定（如目标全不可达），但已记录每条的原因。
- 报告中明确标注无法复测的原因。
